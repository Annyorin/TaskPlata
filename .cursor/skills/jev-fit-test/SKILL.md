# Jev Fit Test

Собери локальный эксперимент на задачах пользователя и ответь на один вопрос: **есть ли в его процессе участок, где Jev полезнее полноценного вызова основного агента?**

Не пытайся доказать пользу Jev заранее. Отрицательный результат — полноценный результат.

## Результат

В рабочей папке должен появиться каталог `jev-fit-test/`:

```text
jev-fit-test/
├── app/                    # локальный стенд
├── data/                   # обезличенные входные примеры
├── runs/                   # фактические ответы и метрики
├── protocol.md             # зафиксированный до запуска протокол
└── report.md               # вывод по конкретным задачам
```

Стенд показывает:

1. исходную задачу или набор данных;
2. путь основного агента самостоятельно;
3. путь Jev отдельно, только в пределах его реальной роли;
4. путь Jev + основной агент;
5. качество, полное время, стоимость и метрики отдельных этапов;
6. ошибки, спорные решения и исходники, к которым они относятся;
7. вывод: `подходит`, `не подходит` или `нужен дополнительный прогон`.

## Фаза 0. Проверка применимости

Сначала изучи 2–5 реальных типовых задач пользователя. Не проси большой датасет, если достаточно нескольких примеров из текущего проекта.

Найди внутри процесса решение, которое одновременно:

- повторяется много раз;
- имеет конечный набор допустимых ответов или явную шкалу;
- отделяется от последующего исполнения;
- проверяется по заранее заданным критериям;
- допускает безопасную передачу спорных случаев агенту или человеку.

Подходящие участки: классификация, маршрутизация, выбор скилла, оценка срочности, проверка правила, фильтрация кандидатов.

Неподходящие участки: написание исследования, создание интерфейса, генерация кода, синтез стратегии, единичный вопрос без повторений.

Если подходящего решения нет:

1. создай короткий `report.md` с объяснением;
2. покажи, где основной агент и так решает задачу одним вызовом;
3. не подключай API и не строй декоративный стенд;
4. остановись с вердиктом `не подходит`.

## Фаза 1. Зафиксировать протокол

До любых модельных запусков создай `protocol.md`. Используй [references/protocol.md](references/protocol.md).

Обязательно зафиксируй:

- исходные данные и их происхождение;
- основной агент, модель, effort и доступные инструменты;
- ограниченное решение, которое принимает Jev;
- критерии качества и ожидаемые ответы, если они известны;
- правило передачи спорных решений;
- одинаковую финальную задачу для двух рабочих путей;
- способ измерения времени и стоимости;
- число повторов;
- ограничения эксперимента.

Критерии качества нельзя придумывать после просмотра ответов.

### Три пути

**A. Основной агент самостоятельно**

Основной агент получает все исходные данные, сам принимает промежуточные решения и выполняет финальную задачу.

**B. Jev отдельно**

Jev выполняет только ограниченное решение. Если задача требует текста, кода или интерфейса, честно показывай отсутствие готового артефакта. Не сравнивай это с завершённой работой агента как равные результаты.

**C. Jev + основной агент**

Jev принимает ограниченные решения. Основной агент повторно разбирает только случаи, которые попали под заранее заданное правило проверки, а затем выполняет ту же финальную задачу, что и в пути A.

## Фаза 2. Собрать стенд

Используй существующий стек проекта. Если подходящего приложения нет, собери компактный Vite + React + TypeScript стенд.

Главный экран — один адаптивный канвас:

- задача или набор данных сверху;
- три пути рядом на широком экране и последовательно на мобильном;
- реальные стадии каждого пути;
- итоговый артефакт или честное объяснение, почему его нет;
- время и стоимость в нижней части карточки;
- раскрываемые исходные данные, решения, проверки и ошибки;
- сохранённая история прогонов;
- заметная маркировка синтетических данных и тестовых ответов.

Не зашивай победителя, ответы моделей или итоговые числа в интерфейс. Демо-фикстуры разрешены только для UI-тестов и должны храниться отдельно от реальных прогонов.

### Данные и секреты

- API-ключи храни только в переменных окружения или памяти локального процесса.
- Не записывай ключи в `runs/`, клиентский код или отчёт.
- Перед отправкой пользовательских данных внешнему API явно сообщи, какие данные уйдут провайдеру.
- Не отправляй конфиденциальные данные без явного разрешения.
- Сервер по умолчанию слушает только `127.0.0.1`.

### Актуальность интеграции

Перед реализацией сверь текущий формат API, модель и тариф только по официальной документации TypeSafe:

- `https://docs.typesafe.ai/api`
- `https://docs.typesafe.ai/models`
- `https://docs.typesafe.ai/confidence`

Не копируй тариф или имя модели из старого примера без проверки.

## Фаза 3. Сухой прогон и разрешение

До платных вызовов:

1. проверь сборку и локальный интерфейс на явно обозначенных фикстурах;
2. покажи пользователю протокол, число запланированных вызовов и ориентировочный расход;
3. запроси явное подтверждение на модельные вызовы;
4. без подтверждения остановись на готовом стенде.

Один подтверждённый запуск не разрешает бесконечные повторы. Для дополнительной серии запроси новое подтверждение с количеством и оценкой стоимости.

## Фаза 4. Провести сравнение

Для одного быстрого теста допустим один прогон каждого рабочего пути. Для устойчивого вывода предложи минимум три повтора с чередованием порядка A/C, но запускай их только после согласования стоимости.

Измеряй отдельно:

- решение Jev;
- решение основного агента;
- повторную проверку спорных случаев;
- финальное исполнение;
- полный путь;
- входные и выходные токены;
- расчётную или сообщённую провайдером стоимость;
- качество промежуточных решений;
- качество финального результата.

Не приписывай всю разницу полного пути Jev, если она возникла на вариативном этапе генерации основного агента.

## Фаза 5. Сформулировать вердикт

Сначала покажи самый сильный подтверждённый результат. Затем сразу обозначь область измерения.

Используй один из вердиктов:

- **Подходит:** качество не вышло за согласованный допуск, а повторяемый этап или полный путь заметно улучшились.
- **Не подходит:** дополнительный вызов не дал выигрыша, ухудшил качество либо сам процесс не содержит подходящего решения.
- **Нужен дополнительный прогон:** результат зависит от вариативного исполнения, выборка мала или пути получили неэквивалентные условия.

В `report.md` разделяй:

1. что измерено напрямую;
2. что можно предположить;
3. чего эксперимент не доказывает;
4. какой следующий тест сильнее всего уменьшит неопределённость.

Финальная формулировка должна отвечать на практический вопрос пользователя: **в какой конкретной точке процесса вызывать Jev, что оставить основному агенту и стоит ли поддерживать эту интеграцию**.

## Чего не делать

- Не сравнивай Jev и основной агент как взаимозаменяемые генеративные модели.
- Не выдавай выбор скилла за выполненную задачу.
- Не используй разные исходные данные, критерии или инструменты в сравниваемых путях.
- Не называй один прогон бенчмарком.
- Не скрывай ошибки ради крупной цифры.
- Не обещай экономию по стоимости подписки на основании справочной API-оценки.
- Не запускай платные запросы автоматически.
