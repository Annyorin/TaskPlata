# Figma to Proto: из макетов в живой прототип

Задача скилла: макеты, собранные по дизайн-системе в Figma, становятся работающим прототипом на React. Главный принцип: переносится поведение, а не вёрстка. Иначе выходит картинка на React: выглядит как приложение, но чипы не нажимаются, а после тапа ничего не происходит.

Для работы нужен Figma MCP. Работа в три этапа, строго по порядку.

## Этап 0: Где живёт код

Спроси пользователя, какой из двух случаев у него:

**А. Кодовая база уже есть** (свой проект или репозиторий команды). Если это репозиторий команды: попроси пользователя завести отдельную ветку и работай только в ней: так ничего не сломаешь, а компоненты команды переиспользуешь как есть. Изучи структуру: где лежат компоненты, какая система токенов/темы, как запускается проект. Ничего не переписывай в чужих файлах: только добавляй свои экраны и используй существующие компоненты.

**Б. Кода ещё нет.** Разверни минимальный стек: Vite + React, один файл токенов (перенеси переменные из Figma в CSS-переменные), папка `src/components/` под компоненты и `src/screens/` под экраны. Не тяни тяжёлые UI-библиотеки: компоненты собираются свои, по макетам.

## Этап 1: Карта соответствий Figma ↔ код

Сердце скилла. Прежде чем собирать экраны, построй файл `proto-map.md` в корне проекта:

```
| Figma-компонент | Код | Статус |
|---|---|---|
| Button (primary, secondary) | src/components/Button.tsx | есть |
| ListRow | src/components/ListRow.tsx | есть |
| ChatBubble | — | создать по макету |
```

Как строить: пройди по макетам переносимых экранов в Figma, выпиши все использованные компоненты (метаданными, без выгрузки полных узлов), сопоставь с тем, что есть в коде по именам и по виду. Три статуса: «есть» (переиспользуем), «создать» (нет в коде: собираешь новый по макету и токенам), «расхождение» (есть, но выглядит иначе: покажи пользователю, пусть решит, чей вариант правда).

Правила карты:
- Дивы заново не рисуем: если компонент есть в коде, используется он, даже если проще написать свой.
- Новые компоненты собираются на токенах, не на пиксельных значениях из макета.
- Карту держи актуальной: добавил компонент: добавь строку.

## Этап 2: Перенос экранов

По одному экрану за заход, в порядке основного пользовательского флоу:

1. Прочитай макет экрана из Figma: структура, состояния, тексты, данные.
2. Собери экран из компонентов по карте. Данные: правдоподобные моки в отдельном файле (`src/data/`), не захардкоженные в разметке строки.
3. **Поведение сразу**: каждый интерактивный элемент отвечает: переход, изменение на месте или понятный отклик. Молчание после тапа это дефект, а не «доделаем потом».
4. Навигация между экранами анимирована: резкая подмена экрана читается как баг.
5. Проверь себя: открой экран, сравни с макетом, пройди все тапы. Что показано, то работает.

После каждого экрана: короткий итог и стоп, если пользователь ведёт процесс пошагово.

## Этап 3: Edge-кейсы

Макет показывает счастливый путь. Прототип обязан пережить края. Пройди список по каждому экрану:

- Пустое состояние: нет данных: что видит пользователь и понятно ли, что делать.
- Ошибка: действие не удалось: есть сообщение и путь назад.
- Длинные тексты: имена, суммы, заголовки в полтора раза длиннее макетных: ничего не обрезается молча и не ломает сетку.
- Экстремальные данные: ноль, отрицательные, очень большие числа.
- Быстрые повторные тапы: ничего не задваивается.

Найденное чини сразу; список проверенного покажи пользователю таблицей.

## Чего скилл не делает

- Не продакшен: без бэкенда, авторизации и деплой-инфраструктуры. Это прототип для проверки гипотез и демонстрации.
- Не трогает чужой код: в командном репозитории только своя ветка и только добавление.
- Не заменяет дизайн-решения: расхождения макета и кода решает пользователь.
