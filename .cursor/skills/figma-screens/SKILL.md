# figma-screens: экраны в Figma по дизайн-системе

Задача скилла: агент собирает экраны в Figma так, чтобы они были консистентны между собой и с уже существующими экранами системы. Главный принцип: **экран это композиция инстансов из библиотеки, а не рисунок**. Всё, что читаемо и повторяемо, берётся из компонентов, стилей и переменных. Руками рисуются только уникальные для экрана вещи, и то на токенах.

Полный рецепт с кодом для `use_figma` лежит в `references/playbook.md`. Приёмка и проверка консистентности в `references/checklist.md`. Читай их перед первым вызовом записи.

## Перед первым вызовом

1. Figma MCP подключён, у пользователя полное место в Figma (право записи в файл). Перед `use_figma` загрузи скилл `figma-use` (Figma сама его раздаёт).
2. Уточни у пользователя: ссылка на файл, как называется страница с компонентами, как называется страница с экранами, размер фрейма экрана (например 390 на 844 для мобильного). Если есть папка `ds/` с индексом, прочитай `ds/INDEX.md` или `ds/components.md`, чтобы выбирать компоненты по назначению, а не по догадке.
3. Пролог сессии: одним read-only проходом собери карту «имя компонента → узел», список текстовых стилей, список переменных и шрифты, которые нужно загрузить. Держи карту в памяти сессии, в файлы не пиши: ID меняются при пересборке компонентов.

## Порядок работы над экраном

1. **План текстом.** До любой записи покажи пользователю состав экрана: какие компоненты, в каком порядке, какие тексты и данные. Дождись подтверждения. Текст бесплатен, перерисовка нет.
2. **Каркас.** Фрейм экрана фиксированного размера, вертикальный авто-лейаут, `clipsContent`. Верх и низ экрана из компонентов системы (статус-бар, апбар, таббар, индикатор), если они есть. Середина это растущий контейнер контента с отступами рамки из токенов. Экраны одного флоу кладутся в ряд с одинаковым шагом.
3. **Содержимое.** Инстансы через `createInstance()` от мастеров из карты. Вариант выбирается по имени свойства. Подписи компонентов сначала через component properties, если их нет, правкой текстового узла. Все дефолтные тексты компонентов подменяются явно, чужой текст из библиотеки на экране это ошибка.
4. **Текст и цвет.** Текст только текстовыми стилями системы, цвет только привязкой к переменной. Прибитые hex и размеры шрифта запрещены. Если нужного токена нет, спроси пользователя.
5. **Три закона размеров.** Высота от содержимого, ширина от родителя, доли масштабированием. Подробно в плейбуке. Нарушение любого из трёх это гарантированный разъезд на следующем экране.
6. **Проверка отдельным вызовом.** После записи не в том же вызове, а следующим, read-only: инстансы настоящие, стили на месте, привязки цветов есть, текст не обрезан. Потом скриншот пользователю.
7. **Консистентность флоу.** Одинаковые этапы на разных экранах выполняются одинаковыми компонентами. Повторяющийся блок на трёх и более экранах это кандидат в компонент: предложи пользователю вынести, сам в библиотеку не лезь без подтверждения.

## Правила без исключений

- **ID не хранить.** Ни в файлах, ни между сессиями. Карта по именам собирается прологом в начале каждой сессии.
- **Компонент внутри компонента не создавать.** Верхний узел компонента через `createComponent`, всё вложенное обычными фреймами.
- **Никакого `throw` в конце мутирующего вызова.** Транзакция откатит всё. Отчёт отдельным read-only вызовом.
- **Страницу переключать один раз за скрипт.** Чужую страницу перед чтением загружать через `loadAsync`.
- **Не собирать в файле с чужими коллекциями переменных.** Дубликаты коллекций ломают привязки. Библиотека подключается к файлу экранов.
- **Не перерисовывать уже собранное** без явного запроса. Если экран есть, правится он, а не создаётся второй.

## Когда чего-то нет

- Нет компонента под задачу: не рисуй заменитель. Скажи пользователю, чего не хватает, предложи собрать компонент в библиотеке по правилам плейбука, и только потом экран.
- Нет текстового стиля нужного размера: спроси, каким пользоваться. Прибивать размер нельзя.
- Компонент не тянется по ширине: это дефект компонента, а не экрана. Покажи пользователю, почини компонент по третьему закону, потом экран.

## Чек-лист перед сдачей экрана

- [ ] План был показан и подтверждён до записи
- [ ] Каркас стандартный: фрейм, авто-лейаут, верх и низ из компонентов, середина растёт
- [ ] Всё повторяемое это инстансы, не фреймы-подделки
- [ ] Текст стилями, цвет переменными, ни одного прибитого значения
- [ ] Три закона размеров соблюдены, экран проверен на ширине 500 и с текстом вдвое длиннее
- [ ] Дефолтные тексты компонентов подменены
- [ ] Проверка сделана отдельным read-only вызовом, скриншот показан
- [ ] Экран стоит в ряду флоу с тем же шагом, что и остальные
